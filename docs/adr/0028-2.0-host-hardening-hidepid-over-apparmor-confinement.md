# ADR-0028: 2.0 호스트 데몬 하드닝 — D8 hidepid + capabilities (AppArmor 데몬-confinement 미배포)

날짜: 2026-07-18
상태: accepted (2026-07-18 사용자 승인)
관계: ADR-0026(1.0 호스트 데몬 MAC — seccomp/NNP 배제 + capabilities + AppArmor)을 2.0-특화 보완. 2.0에서는 본 ADR이 우선.

## 맥락

- **ADR-0026(1.0)**: seccomp/NNP를 LXC 비호환으로 배제하고, 호스트 통제를 **capabilities + AppArmor MAC 프로필**(complain→enforce)로 채택. 1.0은 `.73`(파일럿)·`.100`(프로덕션)에서 AppArmor **enforce 0-DENIED 실증**(VM clone·컨테이너·OVA 포함)으로 롤아웃 완료(v1.3.3~1.3.7).
- **2.0 D8**: iSCSI CHAP 비번의 world-readable `/proc/*/cmdline` 노출(D4 target + D7 initiator)을 `/proc` **hidepid=2 + gid=pcvmon** 로 소거. 1.0에는 없는 2.0 고유 하드닝(V1/V2/deb/재부팅 생존 검증 완료).
- **M5**(main v1.3.7 병합)로 ADR-0026의 AppArmor 프로필이 2.0에 complain으로 유입.

## 문제 (실증)

2.0 검증 호스트(hidepid=2)에서 AppArmor 프로필을 데몬에 confine(complain)하자 **데몬 libvirt 연결이 파손(DEGRADED)** — `virConnectOpen: "Cannot find start time for pid"`. 근본 원인(포렌식):

- **hidepid=2 가 타 프로세스 `/proc/<pid>` 접근을 커널 `ptrace_may_access()` 로 게이트** → 그 경로가 **AppArmor ptrace 매개를 발동**.
- libvirtd(서버)가 연결 클라이언트(데몬)의 `/proc/stat` 을 identity로 읽으려 함 → libvirtd 배포판 프로필은 `ptrace (read) peer=unconfined/@{profile_name}` 만 허용 → **커스텀-confined `usr.local.bin.purecvisorsd` 미커버 → DENIED(397건)** → libvirt 파손.
- **1.0 대조 호스트(hidepid 없음)로 조합이 원인임을 확인**: AppArmor enforce + confined libvirtd라도 **hidepid 없으면 libvirt 정상**(ptrace DENIED 0). `/proc/stat`이 일반 파일 read로 처리되어 ptrace 매개가 발동하지 않고 AppArmor 파일 규칙이 허용한다.
- **셋 중 둘만으로는 무해**: hidepid만 정상, AppArmor만 정상, **hidepid+AppArmor 조합은 파손**. 따라서 **1.0 enforce는 hidepid를 사용하지 않아 안전**하며(ADR-0026 유효), 이 충돌은 **2.0 고유**다.

## 결정

**2.0 호스트 데몬 하드닝 = capabilities(유지) + D8 hidepid(유지). AppArmor 데몬-self-confinement은 2.0에 배포·enforce 하지 않는다.**

1. **D8 hidepid 유지** — D4/D7(CHAP argv) 노출을 실증 소거했고 재부팅 생존·롤백까지 검증됨. 2.0 보안 태세의 핵심.
2. **AppArmor 데몬-confinement 미배포** — hidepid와 이 환경(Ubuntu 24.04 + confined libvirtd)에서 상호배타. deb는 프로필 파일을 유입(1.0 공유 아티팩트)하되, **2.0 데몬을 프로필로 confine/enforce 하지 않는다**. 프로필 파일이 `/etc/apparmor.d/` 에 존재하면 부팅 시 `apparmor.service` 가 자동 로드하고(v1.3.6~ 프로필은 in-file `flags=(complain)` 제거된 **enforce-default**) 그 즉시 confine 되므로, "파일만 두고 부착 안 함"은 차단 심링크 없이는 성립하지 않는다. 따라서 deb postinst 의 계약은:
   - **① 부팅 자동 로드 차단** — `/etc/apparmor.d/disable/usr.local.bin.purecvisorsd` 심링크 생성(멱등).
   - **② 설치 중 로드 금지** — 프로필을 부착하는 `apparmor_parser` 호출 없음. 액션 플래그가 없으면 add 가 기본값이므로 `-r`뿐 아니라 `-a`·`--add`·무플래그·`-C`(complain) 단독 호출도 전부 금지다 — complain 부착만으로도 파손이므로 "감사-only 로드"도 하지 않는다.
   - **③ 로드분 해제** — 커널에 남은 프로필을 `apparmor_parser -R` 로 언로드(실패 무해). 구 스킴의 `force-complain` 심링크도 제거.

   ①②③은 **매 `configure` 마다 조건 없이 수행된다** — 첫 설치·업그레이드·재설치·`dpkg-reconfigure` 구분이 없다. 특히 ③은 "1.x 업그레이드일 때만"이 아니라 항상 실행되며(1.x enforce/complain LIVE 노드 업그레이드가 주 동기일 뿐), 그 결과 **운영자가 명시 opt-in 으로 부착해 둔 상태도 매번 미부착으로 리셋된다**(의도된 동작 — 안전측 기본값 수렴). 재부착은 **운영자 명시 opt-in**(`pcv-apparmor enforce|complain`, ADR-0028 경고 출력 + disable 심링크 제거)으로만 일어난다. 프로필은 1.0 라인·참조용으로 존치.
3. **VM(libvirt per-domain)·컨테이너(lxc per-container) 런타임 격리는 그대로** — 데몬 self-confinement과 무관.

## 대안

- **hidepid 포기 + AppArmor enforce**: D4/D7 CHAP 노출 재개방 + D8 되돌림. 기각(입증된 노출 소거를 잃음).
- **양립 — libvirtd 로컬 override**: `/etc/apparmor.d/local/usr.sbin.libvirtd` 에 `ptrace (read) peer=usr.local.bin.purecvisorsd,` 추가 시 hidepid-발동 ptrace 매개 통과 → 둘 다 가능. 단 **배포판 libvirtd 프로필을 우리 패키지가 패치**(postinst)해야 함 → libvirt 업데이트·타 배포판 강결합·취약. AppArmor MAC 이 전략적으로 필수일 때만 재검토.
- **채택: hidepid 유지 + AppArmor 데몬-confinement 미배포**.

## 결과

- 2.0 데몬은 AppArmor로 self-confine 되지 않는다(1.0 enforce와 상이). 호스트 통제는 capabilities 축소 + hidepid + 게스트/컨테이너 런타임 격리.
- **운영자 opt-in 부착은 패키지 업그레이드·재구성에서 보존되지 않는다** — postinst 가 매 `configure` 마다 disable 심링크를 재생성하고 로드분을 해제하므로, `pcv-apparmor enforce|complain` 은 그때마다 다시 실행해야 하는 명시 행위다(1.x postinst 가 심링크로 모드를 보존하던 것과 상이).
- D4/D7 노출은 hidepid로 소거(유효). MAC 계층 부재의 잔여 위험은 capabilities+hidepid로 수용(ADR-0026이 seccomp을 배제하며 MODERATE 수용한 것과 동류).
- ADR-0026(1.0)은 hidepid 없는 환경에서 유효; 2.0(hidepid)에서는 본 ADR이 우선.
- **1.0 함의**: 1.0이 향후 hidepid를 도입하면 동일 충돌 발생 — 그때 libvirtd override or 하나 배제 결정 필요. 현재 1.0(hidepid無) enforce는 안전.

## 후속

- **⚠️ 2.0 → 1.x 다운그레이드 주의**: 2.0 이 남긴 `/etc/apparmor.d/disable/usr.local.bin.purecvisorsd` 심링크는 1.x 패키지가 지우지 않는다. 그대로 1.x 로 되돌리면 1.0 라인이 전제하는 MAC(complain/enforce)이 **무증상으로 무력화**된다(설치는 성공하고 로그도 조용하다). 되돌릴 때는 반드시 심링크를 제거하고 모드를 재지정한다: `rm -f /etc/apparmor.d/disable/usr.local.bin.purecvisorsd && pcv-apparmor complain`(또는 `enforce`) → `pcv-apparmor status` 로 확인.
- **패키징 정렬(2026-07-27)**: 결정 2를 채택한 시점의 deb postinst 는 여전히 첫 설치 시 force-complain 심링크 + `apparmor_parser -r -W -C`(=complain **부착**)를 수행하고 있어 본 ADR과 모순이었다. 위 ①②③ 계약으로 `packaging/deb/build-deb.sh` 를 시정하고, 회귀는 `scripts/check_deb_apparmor.py`(+ `scripts/tests/test_deb_apparmor.py` 반사실 self-test, `make check-deb-apparmor`)로 고정.
- **ADR 번호 충돌 정리(M5 드리프트)**: 병합으로 `0025`(counterfactual↔tls-always)·`0026`(mac-hardening↔sg-overlay)가 2.0에 공번 — 정본 매핑·해소 플랜은 [`../ADR_INDEX.md`](../ADR_INDEX.md) "⚠️ 번호 충돌 (0025·0026)" 절에 명시. 실제 재번호(소스 주석 동반)는 검증 수반 구현 세션으로 이관.
